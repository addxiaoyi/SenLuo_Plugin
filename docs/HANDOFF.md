# 森罗全系列开发交接

2026-11-19。目标平台为 Minecraft 1.21.11、Paper 132／Folia 14、CraftEngine 26.9.1。运行服用 Java 21，构建根工程同时准备 JDK 21 和 JDK 25。

## 在新设备恢复

1. 克隆仓库并切到 `main`。已有工作区先检查本地改动，再用 `git pull --ff-only` 同步。
2. 按 [新设备构建](../README.md#新设备构建) 恢复仓库同级 `.references/` 下的五个固定源码 checkout，并安装两组 Python 依赖。上游地址与提交见 [来源锁定](research/organization-checkouts.json)。
3. 从仓库根目录运行厨房和系列导入检查，然后跑 Python、Java 测试和 JAR 构建。Windows 可在 PowerShell 使用以下命令。

```powershell
git clone --branch main https://github.com/addxiaoyi/SenLuo_Plugin.git
Set-Location SenLuo_Plugin
# 先按 README 恢复固定源码、.venv 和 JDK
.\.venv\Scripts\python.exe tools\export_cookery_catalog.py --source ..\.references\KaleidoscopeCookery --check
.\.venv\Scripts\python.exe series\tools\import_sources.py --check
.\.venv\Scripts\python.exe tools\build_all.py
```

4. 重新导出 [厨房内容包](../examples/kitchen-pack/README.md) 和 [四个独立系列内容包](../series/README.md#构建与验证)。按 [隔离服准备](../README.md#隔离服准备) 安装 JAR、内容包、CraftEngine 运行 JAR 和默认资源。生成包、原版客户端、Paper/Folia 运行 JAR 和测试世界需在新设备准备。

## 2026-11-19 礼盒提交与饮品致死归因修复

礼盒只读取 STRING 类型的奖品记录，损坏类型不再从监听器抛错，也不覆盖原记录。入口核对事件物品与实际主手的完整组件和数量；交易事件结束后、写背包前再次检查插件仍启用、所选槽位与完整手持快照。仅切换热栏但不改变存储槽、交易回调禁用插件、组件或数量变化、取消与同步重入均保留现有交易守恒语义，成功交换之后才通知收藏。

血腥玛丽使用本次死亡 `DamageSource.causingEntity` 中的玩家，包括归属于该玩家的投射物；不会将环境或其他生物的致死来源回退到历史 `getKiller()`。MONITOR 处理先前未取消的死亡，回血仍发布可取消、可改额的 MAGIC 治疗事件，按回调后的最大生命封顶，并拒绝非法治疗额及回调中的死亡、离线、禁用和区域归属漂移。继续保留同区域限制，非玩家完整饮用链与跨区域归因尚未补齐。

农夫套装主规则原已存在，本轮只复用现有 `InventoryUtils.wrap` 解码入口并补回归，纠正“套装未实现”的旧文档。测试覆盖解码后的四槽完整 ID、两种草帽、精确药效参数、标准取消返回、自然过期行为，以及玩家实体调度、死亡、退出、退役与关闭；不将 mock 解码结果当作真实 CE 装备识别或客户端验收。

本轮累计 745 项 Java 测试通过：Cookery 582、common 30、Doll 43、Tavern 59、Deco 17、MusicPlus 14；Python 223 项（根工具 165＋系列 58）和 Node 场景契约 75 项通过。新增 Java 50 项。本轮分层结果见[礼盒与效果回归证据](research/series-effects-gift-regression-2026-11-19.json)。下方 `01778f8` 的双端重启记录保留为该提交的历史证据，不作为本轮新 JAR 已实服通过的依据。原版 GPU 客户端、独立卸载／热重载、跨区、保护与性能、CE watchdog 根因和许可证条件继续按各自清单推进。

## 2026-11-19 事务与物品状态修复

家具交互入口使用原子闸门，覆盖保护回调和交易事件的同步重入。交易在取消、玩家状态及库存漂移检查之后才提交家具状态；沙发变体拒绝、换槽、家具失效时不扣染料。酒桶、瓶子、果盆、雪克杯和葡萄操作同样复核原状态；自动转移与 ticker 跳过正在交互的家具。抽奖投递和移动玩偶回收各有独立闸门，实体移除回调发生在库存提交之后，收藏先保存再发布通知。

真实协议验收首次发现沙发拆装后恢复默认样式。CraftEngine 26.9.1 先调用家具的 `onLoad/onPlace`，再恢复物品自定义数据；Deco 与 Doll 现会在成功读取物品状态后重新同步显示和未来掉落物。坏存档仍阻断操作并保留原始恢复数据。失败记录保留，未放宽重放断言。

MIDI 计时改为整数商与余数累计，精确处理 tempo 和 SMPTE 30-drop，极端分辨率安全处理乘法溢出；过密音符在解析阶段拒绝整曲，任务句柄登记检查曲目令牌。该轮当时共 668 项 Java、214 项 Python 测试通过，当前累计结果见上方礼盒与效果回归。验收运行器现在严格核对启动 smoke、退出码、超时与正常停服，异常收尾清理资源下载和 Java 解码进程。

## 2026-11-19 重启持久化与定时器修复

新放置的抽奖机、酒桶和果盆没有对应保存键时，按正常空白状态加载；已知键中的错误类型、损坏内容或未知版本仍阻断操作，并保留原始记录。雪克杯适配 CE 在 `onLoad/onPlace` 之后才读取物品数据的顺序，先完成内容编码再同步家具内容与未来掉落物，失败时保留来源物品快照。

酒桶、果盆、雪克杯、龙头、葡萄和抽奖机的六种同步 ticker 不再捕获旧控制器。每次回调以元数据实体查当前映射并核对 UUID，再按控制器类型及同类序号定位；其他行为前置或重排不会让自定义 ticker 停止，同类多个控制器分别执行一次。当前映射、对应控制器或同类序号缺失时直接跳过，不回退到旧实例。

新增回归覆盖沙发红色左段、玩偶全部九轴姿态与未来掉落物的 `saveCustomData → NBT 字节 → 新控制器 → loadCustomData/onLoad` 恢复，玩家修改的 dirty 标记，容器内容恢复和损坏数据保留，以及 CE 真实 Dual/Composite 控制器的有界匹配与防重复派发。该重启检查点当时累计 695 项 Java 测试通过：Cookery 567、common 30、Doll 26、Tavern 41、Deco 17、MusicPlus 14；223 项 Python 测试通过：根工具 165、系列工具 58；75 项 Node 协议场景合同测试通过。

验收探针在 `FurnitureInteractEvent` 的 MONITOR 阶段只观察两名夹具玩家的交互并记录回执计数，取消事件也可见；计数与快照均限制在同一夹具区域。单目标交互只发送一次点击，随后等待该玩家回执增长与目标状态同时成立，并在每次快照核对物品、掉落等不变量；取消和无操作点击也须先收到回执。Doll 九轴逐次等待完整预期姿态和新菜单窗口 ID 后才点击下一轴，避免旧菜单与控制台快照先于网络交互造成误判。

双人并发剪取各向同一旧碰撞盒发送一次请求。首剪可能更换碰撞盒 ID，后请求因旧 ID 失效而不触发事件；此场景要求至少一名玩家的回执增长、两端看到空展板与唯一一朵掉落，缺第二份回执时还必须核对碰撞盒 ID 已更换。之后第二玩家再对新 ID 空剪，严格等待其回执并核对无额外掉落。报告分别记录尝试玩家与实际收到回执的玩家，不将两次发送写作两个控制器均已收到。拾取追踪可在网络实体消失时停止行走，随后仍须由服务端库存证明玩家归属、参与玩家相对基线合计恰好新增一件及原状态 PDC 完整；网络 `entityGone` 本身不视为拾取成功。这些是验收同步机制，不扩大既有验收范围。

展板测试的“满库存”仅指 36 个存储槽均已占用，同色红花仍可合并。记录唯一返花前库存必须不变；记录后只允许双方相对基线合计新增 0 或 1 件同 ID、同数据返花，其他槽位及快照中的 PDC 保持原样。进入下一夹具清库存前，服务端库存差分必须证明合计新增恰好一朵。需要腾格时，经普通库存点击将一组 64 圆石移入空副手，等待服务端存储槽腾出及副手网络状态；只接受光标恰好持有原圆石堆的合法中间态，光标归空后才继续。随后按网络掉落实体位置步行，拾取证明完成后回到原位。
